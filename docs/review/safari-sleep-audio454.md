## Вывод и границы доказанного

Сбой локализован **после DSP-графа, в старом совместно используемом прямом
стереовыходе Web Audio48kHz первой вкладки**, пережившем сон. Сам контекст, осциллятор,
декодированные данные, пользовательский жест и часы работают. И HTML-путь, и другой
прямой выход обходят отказ В ТОЙ ЖЕ вкладке. Это существенно точнее общего «Safari молчит».

Механизм повторного использования подтверждается архитектурой WebKit:
SharedAudioDestinationAdapter keyed by (numberOfOutputChannels, sampleRate),
DefaultAudioDestinationNode::setChannelCount recreates its destination;
suspend/resume только stop/start существующего назначения. Наши системные логи
независимо подтверждают фактическое повторное использование конкретного старого выхода.

Не установлено, какой именно внутренний дефект WebKit/CoreAudio после сна привёл к
беззвучному старому выходу: рассинхронизация ring buffer, состояние AudioUnit и т.п.
Ни один из этих конкретных низкоуровневых вариантов не объявляется доказанным.
Просмотренные публичные исходники main WebKit описывают механизм; это не отладка
точного бинарника установленной Safari27.2.
Причина недоступности native server audio ДО пользовательского перезапуска тоже
не доказана: текущая диагностика уже от нового процесса, а в видимом журнале лаунчера
нет подробного native failure reason. Серверный и браузерный отказы нельзя смешивать.

## Следствия для исправления

Обычного resume, нового контекста с теми же настройками или переключения2->1->2
недостаточно. Нужно гарантированно вывести новый звук из сломанного общего backend,
проверяя реальную слышимость и задержку. Моно и44100 — проверенные ДИАГНОСТИЧЕСКИЕ обходы,
не готовый автоматический production fix. Web Audio->HTML stream тоже звучит, но добавляет
другой транспорт и потенциальную задержку; его нельзя незаметно включать без проверки.

RMS перед destination и advancing currentTime НЕ доказывают физический вывод — у нас оба
признака нормальные в беззвучном состоянии. Текущий зелёный AUDIO означает readiness,
а не подтверждённую акустическую слышимость. Автоматическое решение только по этим
метрикам не обнаружит именно этот отказ. Нужны физические sleep/wake-проверки и явная
процедура проверки/восстановления выхода; нельзя объявлять проблему решённой по Chromium unit tests.

## Актуальный итог: повторный отказ второй вкладки и восстановление

Вторая вкладка отказала и без нового сна. Причину конкретного момента отказа,
включая возможную связь с диагностическими дополнительными контекстами, не доказали.
Предыдущая локализация пути вывода сохраняется, но сон НЕ объявляется единственным
триггером, а смена только числа каналов НЕ считается надёжным исправлением.

Перепроверка с вопросами ПОСЛЕ фактического окончания сигналов:
- Исходный контекст48k/2ch: штатный Start завершился, владелец НЕ услышал.
- HTMLAudio START.mp3 после trusted click: владелец услышал. Первый NotAllowedError
  относился только к предварительному console play() без жеста.
- Независимый контекст44100, тон660Hz: услышал.
- На ТОМ ЖЕ контексте затем вызван speechSynthesis.cancel() (speaking=false,
  pending=false) и повторён тон: услышал. Немедленный отказ от одного cancel()
  в этом контролируемом опыте НЕ воспроизведён. Удалять cancel из кода по этому
  расследованию оснований нет.

Успешное восстановление реального приложения:
1. В stopped-состоянии закрыли неработающий штатный48k контекст второй вкладки
   и контрольный44100 контекст; сервер, страницу и модель часов не перезапускали.
2. Одноразовая обёртка конструктора при следующем trusted pointer gesture дала
   штатной unlockAudio() создать новый контекст44100. Оригинальный window.AudioContext
   восстанавливался самой обёрткой немедленно при конструировании.
3. Штатный Start в аудиопанели прозвучал — подтверждение владельца ПОСЛЕ теста.
4. Удалены все диагностические кнопки/ссылки/функции. Восстановлены исходные
   AudioBufferSourceNode.prototype.start и window.AudioContext. Новый контекст
   ПРИЛОЖЕНИЯ не закрывали; его продолжает использовать обычный код таймера.
5. После очистки отдельно проиграны штатные Start и Finish с паузой; владелец
   подтвердил, что ОБА СЛЫШНЫ. Эти проверки больше не зависели от перехватов.

В конце активна вторая основная вкладка, выбран browser route, реальный штатный
Web Audio работает с44100Hz. Восстановление только в памяти текущей страницы:
постоянного audio fix в исходниках/установщиках НЕТ. Перезагрузка страницы снова
создаст контекст по исходной фабрике. Долговременная устойчивость и задержка/акустическая
синхронность с другими устройствами не проверены. Другие вкладки/сервер не перезапускали.

Следующий шаг — изолированно воспроизвести отказ и реализовать явное управляемое
восстановление browser audio с безопасной отменой старых сигналов и сохранением
временной модели. Нельзя называть проверенный в этой странице44100 универсальной
защитой от всех silent-output состояний или автоматически считать running слышимостью.

## ВАЖНО: подтверждена отмена тестовых сигналов собственным кодом

Владелец перенёс primary в Chrome и наблюдал: тесты то звучат, то молчат,
как при нажатиях раз в секунду, так и после ожидания минимум5секунд.
Chrome primary: stopped/version112, soundAllowed=true, running/unlocked,
serverAudioDisabled=true, serverAudioActive=false. Снимок chrome-test-state.json.

Ограничения: UI cooldown1000ms; серверный GLOBAL rate limit1000ms, превышение429;
тесты запрещены во время активного отсчёта (до отложенного старта допускаются);
команда назначается на now+1800ms+preview offset[-750,+250]; warn даёт5 сигналов
через1000ms. Нет лимита общего количества тестов. Доставка имеет срок годности
и дедупликацию. Сам по себе допустимый новый клик не задуман как запрет следующих
нескольких секунд тишины.

Воспроизведено в изолированном Chromium на отдельном сервере с реальным WebAudio:
reproduce-audio-test-cancellation.cjs. В двух запусках буфер назначался на~1785–1791ms
вперёд, затем через~1–2ms приходил node.stop(0), ended задолго до времени старта.

AudioBufferSourceNode.stop -> clearSignalTimers -> clearStoppedTimerSignals ->
applyServerState -> clientActionTransport.applyRemote -> applyRemoteSafely ->
clientActionTransport.send, phase success. HTTP ответ audioTest применяется после
того, как SSE audio-test уже назначил звук; при stopped state полная очистка
удаляет тест как обычный будущий сигнал таймера. Следующий audioTest/SSE state
также может отменять предыдущие ещё не начавшиеся тесты. Зависимость от порядка
HTTP/SSE объясняет непостоянство. Это подтверждённый дефект scheduler/lifecycle,
не результат аппаратного измерения звука и не доказательство backend-сбоя Chrome.

при running/44100 НЕ доказывает повторной поломки физического вывода Safari:
